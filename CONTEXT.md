# pi-fast-resume

Расширение pi, ускоряющее resume сессий: оригинальный пикер + фоновый индекс метаданных.

## Язык проекта

**Индекс**:
SQLite-база метаданных сессий (`path`, `size`, `mtime`, `id`, `cwd`, `name`, `firstMessage`, счётчики), которую поддерживает worker thread. Единственный источник данных для пикера в нашем расширении. Живёт в `~/.pi/agent/pi-fast-resume/index.db`; производные данные, пересоздаётся при порче без вопросов.
_Не использовать_: кэш (в обсуждениях допустимо, но канон — «индекс»)

**Воркер**:
Worker thread внутри процесса Pi, который сканирует каталог сессий и обновляет индекс. Main thread никогда не читает session-файлы сам.

**Дифф**:
Проход воркера, при котором читаются только новые или изменившиеся файлы (по паре `size`+`mtime`). Холодный первый проход обходит все файлы.

**Потоковый metadata-pass**:
Обработка нового или изменённого JSONL в worker thread через `createReadStream` и построчный JSONL-разбор. Даёт точные `name`, `messageCount`, `lastActivityTime`, `parentSessionPath`, `cwd`, `id` и `firstMessage`, как штатный `SessionManager`; полный текст диалога в индекс не сохраняется.

**Сабагентная сессия**:
Сессия, созданная расширением pi-subagents: признак — поле `parentSession` в header файла и имя вида `<тип>#<8 hex>`. По умолчанию скрывается из списка пикера.

**Резюме-пикер**:
Оригинальный компонент `SessionSelectorComponent` из `@earendil-works/pi-coding-agent`, который наше расширение переиспользует без модификации UI.

**Поисковый корпус**:
Суррогатное поле, которое расширение подставляет в `SessionInfo.allMessagesText` для штатного поиска пикера: `name + firstMessage + cwd`, обрезанное до 4 KB. Полный текст сообщений в индекс не попадает сознательно — см. ADR-0001.
_Не использовать_: allMessagesText как «полный текст сессии»

**Тихое обновление**:
Фоновая подмена списка сессий в открытом пикере после завершения диффа (`setSessions`). Пользователь не видит ни блокировки, ни «Loading».

**Открытие**:
Команды `/rf` и `/resume-fast` (алиасы одного обработчика) открывают резюме-пикер. Шортката нет и не планируется до отдельного решения.

**Ленивый воркер**:
Воркер создаётся при первом вызове `/rf` или `/resume-fast` в текущей Pi-сессии и завершается на `session_shutdown`. Между открытиями пикера остаётся тёплым; периодического таймера нет.

**Точный счётчик**:
`messageCount` и `lastActivityTime` извлекаются потоковым metadata-pass для нового или изменённого JSONL. После успешной записи в индекс это точные значения, как в штатном `/resume`.

**Скрытие сабагентов**:
Пикер по умолчанию исключает сессии pi-subagents; `Ctrl+G` показывает/скрывает их без обращения к диску. Признак сабагента: `parentSessionPath` задан и имя соответствует `/^[^#]+#[0-9a-f]{8}$/i`; обычные fork/clone не скрываются.

**Переименование**:
`Ctrl+R` доступен для любой сессии, включая сабагентную. Операция добавляет в JSONL запись `session_info`; воркер немедленно обновляет один индексный ряд.

**Удаление**:
`Ctrl+D` повторяет штатный picker: подтверждение, `trash`, затем fallback на `unlink`; активная сессия защищена. После успеха запись удаляется из индекса.

**Граница воркера**:
`better-sqlite3` и вся синхронная работа с SQLite разрешены только внутри worker thread. Main thread получает готовые DTO через сообщения и не импортирует драйвер.

**Lease диффа**:
Краткоживущая SQLite-запись, выбирающая ровно один worker-владелец фонового диффа среди нескольких Pi-процессов. Остальные читают готовый индекс; истёкшая lease допускает подхват после аварии владельца.

**Прогрессивный холодный старт**:
При пустом индексе `/rf` сразу открывает пустой пикер со статусом `Index warming up… x/y`. Воркер постепенно наполняет его через `setSessions`; ожидания полного обхода нет.

**Архивная сессия**:
Сессия из каталога `__archive__--…--` внутри `~/.pi/agent/sessions/`. Индексируется и видна в режиме All как в штатном `/resume`; хранит флаг `archived` для будущей маркировки.

**Checkpoint пакета**:
SQLite-транзакция из 25 обработанных session-файлов. После checkpoint результаты доступны пикеру и переживают аварийное завершение Pi; максимум повторяется один незакоммиченный пакет.

**Параллелизм чтения**:
Worker одновременно потоково читает до 10 JSONL — то же ограничение, что в штатном `SessionManager.listAll()`. Чтение параллельное, SQLite-checkpoint остаётся пакетным по 25.
